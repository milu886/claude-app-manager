# 1.0.3 · 系统代理下载修复与镜像滞后处理

- 修复“仅 GitHub”下载来源报 `github.com：fetch failed` 的问题。原因是 Node 内置 `fetch` 不使用 Windows 系统代理：`api.github.com` 可直连，因此能读取版本；`github.com` 直连超时，安装包下载失败。
- 更新清单与安装包请求改走 Electron 网络栈，与浏览器一样遵循系统代理设置。
- 重定向仍以手动模式逐跳交给管理器校验，只允许 HTTPS 和原有白名单域名；SHA-256、大小校验、`.part` 原子保存与取消清理保持不变。
- “国内镜像优先”模式同时查询镜像清单与 GitHub 最新发布，提供较新的版本。镜像清单滞后时（例如镜像停在 `4.29.0`、GitHub 已发布 `4.4212.0`），改用 GitHub 固定版本地址下载；版本相同时仍先走镜像。GitHub 请求失败（如达到请求限制）时沿用上次获得的 GitHub 版本，不会在两个版本间来回跳动，也不影响镜像结果。
- 修复“完成更新”反复停在“等待完成注册”：Claude 桌面端已退出、CoworkVMService 也已停止且进程退出后，Windows 部署日志仍报告 `Claude_pzs8sxrjxfjjc!Claude` 在运行（无“活动服务”事件 9641）。该服务为按命名管道触发启动的打包服务，Claude 包组件可能以普通用户看不到的系统进程保留包标识，导致更新每次都被延后，随后服务又按旧版本恢复。现在：停止服务后等待其进程退出（最长 60 秒，超时报错并恢复服务）；安装前再次确认没有 Claude 桌面进程，此时使用 `-ForceApplicationShutdown` 由 Windows 关闭该包的残留进程并完成注册；桌面端运行（包括刚刚启动）时仍使用延后注册，不中断会话。
- 更新仍被延后时，从 Windows 部署日志（事件 638 / 9641）读取实际占用者，记录在活动记录与“完成更新”说明中，不再只给出笼统提示。
- 实际验证：在系统代理环境中从 GitHub 下载 Claude `4.4212.0` x64 安装包（283,055,488 字节），SHA-256 校验通过；中途取消后无残留部分文件。
- 47 项测试，新增网络通道的手动重定向、未知域名拦截、ETag / 304 复用与取消清理，以及镜像滞后取较新版本、GitHub 失败沿用版本、仅 GitHub 不访问镜像、等待服务进程退出后再部署、进程不退出时阻止部署并恢复服务、空闲时强制关闭残留进程而桌面启动时改为延后，以及延后原因解析。
